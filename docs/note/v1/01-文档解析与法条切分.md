# 阶段 1：文档解析与法条切分：实施笔记

> 版本：V1  
> 对应规划：docs/plan/v1/01-文档解析与法条切分.md  
> 实施状态：done  
> 完成日期：2026-09-29

## 1. 实际完成内容

- 实现 PDF、DOCX、Markdown 三种 loader，并保留来源文件和可用的位置元数据；
- 实现不可见字符、全角空格、异常换行及 PDF 重复页眉页脚清理；
- 实现编、章、节、条的结构识别和层级继承，支持“第 X 条之一”形式；
- 跳过目录中的条号，正确合并跨页法条；
- 默认按条切分，超过阈值时按自然段拆分，不从自然段中间强制截断；
- 生成稳定的 `chunk_id` 和基于正文的 `text_hash`；
- 输出 `data/processed/articles.jsonl` 和 `data/processed/parse_report.json`；
- 为 loader、normalizer、splitter 和全量 pipeline 编写自动化测试。

## 2. 最终实现方案

- PDF：使用 PyMuPDF，以 PDF 查看器中的物理页为 `SourceBlock`，页码从 1 开始；
- DOCX：使用 python-docx，以非空段落为 `SourceBlock`；DOCX 不提供可靠物理页码，因此页码保存为 `null`；
- Markdown：使用 UTF-8 读取，以非空文本行为 `SourceBlock`；页码保存为 `null`；
- 文本清洗：删除零宽字符、BOM 和软连字符，统一全角空格、不间断空格及换行符；
- PDF 页边清理：只在页面顶部和底部候选区域统计重复文本，达到重复阈值后作为页眉页脚删除；
- 法条定位：优先使用正文中最后出现的“第一条”作为正文起点，避免把目录条目切成正文；
- 层级结构：进入新编时清空章和节，进入新章时清空节；“附则”作为独立章级结构处理；
- 跨页处理：当下一页仍属于同一法条且上一页末尾没有结束标点时，拼接为同一自然段；
- 长文拆分：`max_chars=1200`，仅在超长法条存在多个自然段时拆分；单个超长自然段保持完整并写入质量警告；
- ID 规则：`chunk_id` 由稳定的法律 ID、条号、重复序号及必要的子块序号生成；`text_hash` 仅由规范化正文生成；
- 写出策略：JSONL 和质量报告先写临时文件，全部成功后原子替换正式文件。

## 4. 遇到的问题与解决方法

### 问题 1：PDF 中存在零宽字符和视觉换行

- 现象：提取文本包含 `\u200b`，长句会在页面视觉行边界处断开；
- 原因：PDF 保存的是排版位置，不是可靠的逻辑段落结构；
- 解决方法：删除不可见字符，根据结构标题、列举项和句末标点修复视觉换行；
- 如何避免再次发生：新增 PDF 时先检查可提取字符数、不可见字符和跨页条文。

### 问题 2：目录和正文包含重复的章节标题或条号

- 现象：简单地从第一个条号开始切分可能把目录识别成正文；
- 原因：目录和正文使用相同的“第 X 章／第 X 条”格式；
- 解决方法：优先选择最后出现的“第一条”作为正文起点，并用真实文件测试目录过滤；
- 如何避免再次发生：新增不同来源的文件时检查目录格式，必要时扩展正文起点规则。

### 问题 3：跨页法条同时需要正文连续性和页码可追溯性

- 现象：直接合并整份 PDF 会丢失页码；完全按页切分又会拆断法条；
- 原因：文本连续性与来源页定位需要同时保留；
- 解决方法：loader 按页保存，splitter 在同一法条内部有条件地拼接跨页文本，同时记录 `page` 和 `end_page`；
- 如何避免再次发生：对所有 `page < end_page` 的法条执行原文页范围核验。

## 5. 实验和决策记录

| 方案 | 结果 | 是否采用 | 原因 |
|---|---|---|---|
| PDF 全文一次性拼接 | 丢失页码映射 | 不采用 | 无法满足来源追溯要求 |
| PDF 按物理页加载 | 可保留起止页 | 采用 | 便于跨页识别与原文核验 |
| 固定字符数切分所有文本 | 会破坏法条语义边界 | 不采用 | 法律检索单元应优先保持完整条文 |
| 一条法条一个 chunk | 当前最长法条 925 字符 | 采用 | 当前语料无需额外拆分，语义完整 |
| 超长法条按自然段拆分 | 合成测试通过 | 采用 | 为未来新增长文档保留能力 |
| JSONL 原子写出 | 失败时不覆盖已有正式产物 | 采用 | 避免生成半份数据集 |

## 6. 可复用知识

- PDF 的文本可提取不代表结构可靠，必须分别处理页边文本、视觉换行和跨页连续性；
- DOCX 段落结构比 PDF 可靠，但通常没有可直接使用的物理页码；
- 法条切分应优先使用法律自身的结构边界，而不是固定 token 或固定字符窗口；
- 稳定 ID 应基于稳定业务身份，正文变化另外用 `text_hash` 检测；
- 自动报告必须区分法条数与 chunk 数，超长拆分后两者可能不相等；
- 正式数据写出前应全局检查 `chunk_id` 唯一性。

## 7. 遗留问题

- [ ] 新增来源格式差异较大的 PDF 时，需要重新验证页眉页脚和正文起点启发式规则；
- [ ] 当前语料最长法条为 925 字符，尚未在真实语料中触发 1,200 字符拆分，仅有合成测试覆盖；
- [ ] 阶段 2 建立索引时，需要决定检索文本是否拼接法律名、章节名和条号。

- 阶段 2 可以直接读取 `data/processed/articles.jsonl` 建立 BM25 和向量索引；
- `chunk_id` 可直接作为 Chroma 文档 ID 和 BM25 两路结果的合并键；
