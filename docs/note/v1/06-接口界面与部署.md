# 阶段 6：接口、界面与部署：实施笔记

> 版本：V1
> 实施状态：done
> 完成日期：2026-10-17

## 实际交付

- 提供 FastAPI 应用 `rag_law.api.main:app`：`GET /v1/health`、`GET /v1/laws`、`POST /v1/retrieve`、`POST /v1/query`。
- `/v1/query` 复用 `AnswerPipeline`，返回阶段 4 定义的 `AnswerPipelineResult`；`/v1/retrieve` 返回精排后的法条结果。
- API 延迟加载模型与索引，启动和健康检查不读取密钥。健康检查分别报告 manifest、结构化法条、BM25 和 Chroma 是否就绪。
- 提供每 IP 每分钟 30 次的进程内限流与 60 秒请求超时；索引/服务不可用返回 503，超时返回 504，限流返回 429。
- 演示界面已经支持连续问答、法律筛选、法条位置展示和上传法律后的全链重建；CLI 的 `add-document` 仍是等价管理入口。
- 界面的“维护现有知识库”面板提供“重新构建现有知识库”按钮，无需上传新文件即可按 manifest 重跑解析、BM25 和 Chroma；完成后主动提示重启独立 API 进程或容器。
- 保留 Streamlit 顶部工具栏中的侧边栏开关，避免浏览器在窄窗口或记忆折叠状态后无法重新展开维护面板。
- 增加 `Dockerfile` 和 `compose.yaml`。单一锁定镜像同时承载 API 与 Streamlit，Compose 分别暴露 8000 和 8501 端口，并配置独立健康检查。
- `data/`、`indexes/` 与 `logs/` 使用宿主机 bind mount：API 只读挂载知识库，界面保留添加法律和重建索引所需的写权限，日志在容器重建后继续保留。
- Linux 服务器首次从 GitHub 拉取、尚无忽略产物时，可以先启动 `ui` 服务，通过页面全库重建按钮生成 `data/processed/` 和 `indexes/`，再启动或重启 API。

## 隐私与运行边界

`AnswerRunLogger` 写 JSONL 前递归脱敏身份证号、手机号、邮箱、银行卡号和座机号。API 的异常日志只记录异常类型，不记录用户查询原文。

本地以 `uv run uvicorn rag_law.api.main:app --host 127.0.0.1 --port 8000` 启动；详细配置、重建索引与排障说明见 README。进程内限流不适用于多实例部署，生产环境应由反向代理或共享限流存储接管。

镜像直接运行时默认使用 UID 10001 的非 root 用户；Compose 为方便 bind mount，默认用宿主机常见的 `1000:1000`，也可通过 `RAG_LAW_UID`、`RAG_LAW_GID` 调整。Linux 宿主机需要确保挂载目录对该用户具有相应权限。通过界面重建索引后，正在运行的 API 仍持有旧的内存流水线，应执行 `docker compose restart api` 重新加载。

## 验证

增加 `tests/test_api.py`，覆盖健康检查、法律清单、检索 schema、非法法律筛选、超时和限流。依赖锁、API 测试与本地运行由项目维护者完成验证；Docker Compose 配置已通过 YAML 结构、服务、挂载和健康检查字段的静态校验。当前执行机器未安装 Docker CLI，因此镜像构建与容器启动需在装有 Docker Desktop 或 Docker Engine 的部署机上执行 README 中的冒烟验证命令。
