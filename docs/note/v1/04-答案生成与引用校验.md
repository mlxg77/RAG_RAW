## 1. 实际完成内容

- 使用 `ChatOpenAI` 接入 SiliconFlow `Qwen/Qwen3-8B`；
- 使用 `ChatPromptTemplate` 定义首次回答和引用修复两套提示词，提示词版本为 `stage4-v1`；
- 使用 Pydantic `GeneratedAnswer` 和 `with_structured_output` 约束结构化输出；
- 使用 LCEL 组合 Prompt 与结构化 LLM；
- 实现结论、分析、适用条件、引用、限制和追问字段；
- 模型只引用 `E001` 等短 Evidence ID，程序映射回原始 `chunk_id`；
- 严格校验证据 ID、法律名称、条号、展示证据连续子串和原始法条连续子串；
- 引用校验失败时只修复一次，再失败时返回安全降级结果；
- 设置临时 Top1 Rerank 拒答阈值 `0.15`；
- 实现 `answered`、`needs_clarification`、`insufficient_evidence` 和 `generation_failed` 四种状态；
- 新增 `answer` CLI，支持法律名称过滤、阈值覆盖、调试输出和 JSON 输出；

- 完成 96 项自动化回归测试和 7 条真实链路验收。

## 2. 最终实现方案

### 回答流水线

```text
用户问题
  -> 阶段 3 混合检索、精排和上下文构建
  -> Top1 低于 0.15：直接返回 insufficient_evidence
  -> 首次结构化生成
  -> 引用校验
      -> 通过：构造最终 AnswerResponse
      -> 失败：携带错误和原回答修复一次
          -> 通过：构造最终 AnswerResponse
          -> 再失败：返回 generation_failed
  -> 写入脱敏 JSONL 运行日志
```

模型生成的引用结构只包含 `evidence_id`、法律名、条号和引文。通过校验后，程序使用原始法条元数据构造 `ValidatedCitation`，补充 `chunk_id`、`law_id`、来源文件和页码。模型不能直接决定最终展示的追溯字段。

### 低相关度门控

当前临时阈值为 `0.15`。阶段 3 的 24 道可回答题中，已知召回失败的 q019 Top1 为 `0.0176`，其余题最低 Top1 约为 `0.238`，因此暂取两者之间的值。真实验收表明，单一相关度阈值不能识别所有范围外或事实不足问题，阶段 5 必须重新校准并加入显式范围判断。

### 运行日志

默认写入：

```text
logs/answer_runs.jsonl
```

每行是一条独立 JSON，包含运行 ID、UTC 时间、脱敏问题、法律过滤条件、Prompt 版本、模型名、检索结果元数据、脱敏最终回答和延迟指标。`logs/` 已被 Git 忽略。

## 4. 遇到的问题与解决方法

### 问题 1：模型为法律名称添加书名号

- 现象：q002 检索正确命中《道路交通安全法》第九十一条，但模型在 `law_name` 中加入外层书名号，严格字符串校验失败；修复一次后仍重复；
- 当前处理：不放宽校验，第二次失败后安全降级；
- 后续：在阶段 5 对比强化 Schema 描述、提示词示例，以及仅规范化外层书名号三种方案。

### 问题 2：事实不足题没有形成追问

- 现象：q025、q026 均进入两次生成后降级，最终没有返回 `needs_clarification`；
- 当前处理：保留安全降级结果；
- 后续：增加显式回答模式字段或生成前事实充分性判断，并把追问准确率纳入评测。

### 问题 3：相似主题的范围外问题可能获得高分

- 现象：q030 指定不在库中的《个人信息保护法》，Top1 仍达到 `0.707569`；
- 原因：现有身份证法等文本与“个人信息、人脸识别”在语义上相关，相关度阈值不能等同于知识库范围判断；
- 当前处理：模型失败后安全降级；
- 后续：从问题中抽取显式法律名称，并先与 `manifest.yaml` 中的正式名称对比。

### 问题 4：失败路径延迟较高

- 现象：q025 总耗时达到 228.8 秒；
- 原因：阶段 3 包含多次远程 Rerank，LLM 客户端存在传输重试，引用失败后又执行一次修复生成；
- 后续：分别记录单次 LLM 延迟和传输重试次数，重新设置超时，避免多层重试叠加。

## 5. 实验和决策记录

| 方案 | 结果 | 是否采用 | 原因 |
|---|---|---|---|
| `with_structured_output` + function calling | 能返回 Pydantic 对象 | 采用 | Schema 会随工具调用发送给模型 |
| 模型直接输出完整 chunk_id | 尚未使用 | 否 | 长 ID 容易复制错误且浪费上下文 |
| 模型引用短 Evidence ID | 可映射到原始 chunk | 采用 | 便于生成和严格校验 |
| 引用失败无限重试 | 延迟和成本不可控 | 否 | 最多修复一次 |
| 单一 Rerank 阈值作为范围判断 | q030 得分 0.707569 | 临时保留 | 阶段 5 增加显式范围判断 |
| 保存完整 Prompt 和上下文 | 存储量大且增加隐私风险 | 否 | 只记录 Prompt 版本和检索元数据 |
| 当前真实模型表现阻塞阶段收尾 | 4/7 用例未达期望 | 否 | 按项目决策转为明确代办，进入阶段 5 量化处理 |

## 6. 可复用知识

- 结构化输出只保证字段形状，不保证字段值与证据完全一致，仍必须程序校验；
- Evidence ID 应由程序分配，最终 chunk 映射也应由程序完成；
- 低相关度阈值适合快速拒绝明显无关问题，但不能代替知识库范围识别；
- 对模型生成字段进行严格校验时，要明确决定哪些差异属于格式差异，哪些属于事实差异；
- 传输重试和业务重试必须分别计数，否则失败路径延迟可能成倍放大；
- 运行日志应默认最小化，只保存复现和评测必需的数据。

### 回答流水线 answer_pipeline.py 执行流程拆解

`AnswerPipeline` 把阶段 3 的检索、结构化生成、引用校验和安全降级串成一条流水线。一次请求最多调用两次 LLM，所有出口都产出 `AnswerPipelineResult`。

#### 外层 run 与内层 _run 的分工

```text
run(query, law_name, progress_callback)        对外入口
  -> _run(...)                                 真正的业务流水线，不写日志
      -> 抛异常：推送 "error" 进度，logger.exception，原样 raise
  -> run_logger.write(result)                  写 logs/answer_runs.jsonl
      -> 只捕获 OSError / TypeError / ValueError
  -> logger.info 汇总各阶段耗时
  -> 推送 "complete" 进度，返回 result
```

- `run` 只负责异常兜底、写运行日志和通知完成，业务细节都在 `_run`；
- 日志写入失败只记 stderr，不能让一个已经生成的法律回答丢失。

#### _run 主流程：5 步，3 类出口

```text
1. 规范化问题：query.strip()，为空直接 ValueError
2. 检索：retrieval_pipeline.run(...)
     混合召回 -> 精排 -> 构建带 E001 编号的上下文，进度回调透传给 UI
3. 证据门控：_has_sufficient_evidence
     条件：Top1 Rerank 分 >= 0.15 且 evidences 非空 且 context.text 非空
     -> 不满足：出口 A，insufficient_evidence，不调用 LLM，attempts = 0
4. 首次生成：answer_chain.invoke({question, context})
     -> 抛异常或返回值不是 GeneratedAnswer：出口 B，generation_failed
     -> 首次引用校验 citation_validator.validate
         -> 通过：出口 C，_finalize_generated_answer
5. 修复一次：repair_chain.invoke({question, context, previous_answer, validation_errors})
     -> 抛异常或类型不对：出口 B，generation_failed
     -> 二次引用校验
         -> 通过：出口 C，_finalize_generated_answer
         -> 仍失败：出口 B，generation_failed
```

- 修复时把上一轮回答的 JSON（`model_dump_json`）和校验错误清单一起交给模型，让它针对性改正；
- 修复上限是一次，再失败直接降级，不做无限重试；
- 所有出口统一经过 `_build_result` 打包：问题、回答、检索结果、生成次数、Top1 分数、校验错误、Prompt 版本、生成耗时、总耗时。

#### 出口 C 的细分：_finalize_generated_answer

校验通过只说明“没有错误引用”，还要看校验后剩下多少条有效引用：

```text
validation.citations 为空？
  -> 是，且模型给了追问：_clarification_answer，needs_clarification
       只展示追问和适用条件，不展示模型的法律分析
  -> 是，且没有追问：_insufficient_answer，insufficient_evidence
  -> 否，有有效引用：
       -> 有追问：needs_clarification，带分析和引用
       -> 无追问：answered
```

原则：**没有可核验的引用，就不展示模型生成的实质性法律结论**。这也解释了真实验收中 q028 为什么是 `insufficient_evidence` 但生成次数为 1：通过了证据门控、调用了模型，但模型没有给出引用也没有追问。

#### 四种 status 与触发场景

| status | 触发场景 | LLM 调用次数 |
|---|---|---:|
| `answered` | 校验通过、有有效引用、无追问 | 1～2 |
| `needs_clarification` | 校验通过且模型给出追问（有无引用均可） | 1～2 |
| `insufficient_evidence` | 未过证据门控；或校验通过但无引用、无追问 | 0 或 1～2 |
| `generation_failed` | 生成异常、返回类型错误、修复后仍未通过校验 | 1～2 |

#### 贯穿全流程的设计点

- 依赖注入 + Protocol：检索、引用校验、运行日志都用 Protocol 声明接口，由构造函数注入，测试可换成假对象；`AnswerPipeline.load()` 负责组装真实组件；
- 构造时校验 `min_answer_score` 必须在 `[0, 1]`，避免阈值配置错误静默生效；
- 两套计时：`total_started_at` 从检索前开始；`generation_started_at` 通过证据门控后才赋值，所以出口 A 的 `generation_latency_ms` 为 0；
- 内部错误与用户文案分离：`validation_errors` 收集“首次生成：…”“修复生成：…”等诊断信息，只进入结果对象和日志；用户看到的永远是 `_generation_failed_answer()` 等固定安全文案；
- 进度通知走 `_emit_progress`，回调出错不中断流水线，详见下一节。

### 普通调用与回调：以进度回调 ProgressCallback 为例

#### 三个容易混淆的概念

| 概念 | 层面 | 含义 | 在本项目中的体现 |
|---|---|---|---|
| 调用 | 执行动作 | 函数名后面加括号并执行，如 `f(x)` | `pipeline.run(query)`、`callback(stage, message)` |
| 可调用（Callable） | 类型 / 属性 | 能加括号执行的东西：普通函数、lambda、对象方法、带 `__call__` 的实例等 | `ProgressCallback = Callable[[str, str], None]` |
| 回调（callback） | 设计模式 / 用法 | A 把自己写的函数交给 B，由 B 在合适的时机调用 | UI 把 `show_progress` 交给流水线，流水线在每个阶段调用它 |

- 回调不是调用的反面，而是一种特殊的调用：函数由调用方提供，什么时候执行由被调用的一方决定；
- 回调必须是可调用的，但可调用的东西不一定被当作回调使用。比如自己直接写 `show_progress("x", "y")`，只是一次普通调用；
- 一句话概括：用 `Callable` 这个类型，来实现“回调”这种设计。

#### 普通调用与回调的对比

| | 普通调用 | 回调 |
|---|---|---|
| 是不是调用 | 是 | 是 |
| 函数是谁写的 | 被调用的一方 | 调用方自己（UI 写的 `show_progress`） |
| 谁去执行调用 | 调用方 | 被调用的一方（流水线） |
| 调用时机由谁决定 | 调用方 | 执行调用的一方（流水线决定在哪个阶段通知） |

“回”指的是方向：本来是 UI 调用流水线，现在流水线反过来调用了 UI 写的函数。从执行机制看，回调发生的那一行和普通的 `print(...)` 没有区别。

#### 本项目中的定义与声明

```python
# src/rag_law/generation/answer_pipeline.py
from collections.abc import Callable

# 类型别名：接收 (stage, message) 两个字符串，不返回任何值
ProgressCallback = Callable[[str, str], None]


class AnswerPipeline:
    def run(
        self,
        query: str,
        *,
        law_name: str | None = None,
        progress_callback: ProgressCallback | None = None,  # 声明：可以传入一个回调，也可以不传
    ) -> AnswerPipelineResult:
        ...

    @staticmethod
    def _emit_progress(
        callback: ProgressCallback | None,  # 声明：callback 是可调用对象或 None
        stage: str,
        message: str,
    ) -> None:
        logger.info("[RAG] stage=%s message=%s", stage, message)

        if callback is None:  # 先排除 None，否则 None(...) 会报错
            return

        try:
            callback(stage, message)  # 调用：回调真正发生的地方
        except Exception:
            logger.exception("[RAG] progress callback failed at stage=%s", stage)
```

- `ProgressCallback = ...` 和参数标注 `callback: ProgressCallback | None` 是**声明**，告诉编辑器和读代码的人“这里要一个能用两个字符串调用的东西”；
- `callback(stage, message)` 是**调用**，加上括号才会真正执行传进来的函数；
- 起别名 `ProgressCallback` 是为了不在 `run`、`_run`、`_emit_progress`、`RetrievalPipelineProtocol` 里重复写一长串类型，签名要改时也只改一处；
- `knowledge_base.py` 中也定义了同结构的 `ProgressCallback`，供“添加法律并重建索引”报告进度。

#### 为什么用 `Callable` 标注

- 写清调用约定：看类型就知道回调要接收 `(stage, message)`，返回值不会被使用；
- 让静态检查提前发现错误：传入参数个数不对的函数时，Pyright / mypy 会直接标红；否则要等运行时才报 `TypeError`，而且会被 `_emit_progress` 的 `try/except` 吞掉，只在日志中留一条记录；
- 不限定具体形式：普通函数、lambda、对象方法、`functools.partial` 都符合；
- 依赖的只是一个函数时用 `Callable`，依赖的是一个带方法的对象时用 `Protocol`（如 `RetrievalPipelineProtocol`、`CitationValidatorProtocol`）；
- 类型标注在运行时不做检查，它的价值体现在编写代码阶段的提示、静态检查和可读性。

#### 为什么返回值是 `None`

- 回调只是单向通知（流水线 → 界面），流水线调用后不接收也不判断返回值；
- 返回类型写 `None`，等于约定“返回值不影响流程”，写回调的人只需负责展示进度；
- Python 函数不写 `return` 时自动返回 `None`，UI 的 `show_progress` 天然符合；
- 如果以后要支持“用户中途取消”这类需要界面反馈给流水线的功能，才需要改成有返回值的类型（如 `bool`），并在流水线中增加对应判断。

#### UI 交给流水线的函数：show_progress

```python
# src/rag_law/ui/app.py
with st.status("正在准备法律检索…", expanded=True) as progress:  # 每次提问新建一个状态框
    shown_stages: set[str] = set()  # 已写过提示的阶段，用于去重

    def show_progress(stage: str, message: str) -> None:
        state = (
            "complete" if stage == "complete"
            else "error" if stage == "error"
            else "running"
        )
        progress.update(
            label=message,  # 状态框标题换成当前提示
            state=state,  # 进行中 / 完成 / 失败
            expanded=stage not in {"complete", "error"},  # 结束时折叠
        )

        if stage not in shown_stages:  # 同一阶段只追加一行记录
            progress.write(message)
            shown_stages.add(stage)

    result = _load_pipeline().run(
        query,
        law_name=law_name,
        progress_callback=show_progress,  # 传函数本身，不加括号
    )
```

- `progress_callback=show_progress` 传的是函数对象；写成 `show_progress()` 会立刻执行一次，把返回值 `None` 传进去；
- `show_progress` 定义在 `with` 块内部，可以直接使用外层的 `progress` 和 `shown_stages`（闭包），所以流水线只传 `stage` 和 `message`，它也知道该更新哪个状态框。

#### 一次提问中的调用顺序

```text
[普通调用] UI 调用 AnswerPipeline.run(query, progress_callback=show_progress)
  -> [普通调用] run 调用 _run，原样传递 progress_callback
      -> [回调] 检索流水线调用 show_progress("retrieval", ...)
      -> [回调] 检索流水线调用 show_progress("context_building", ...)
      -> [回调] _run 调用 show_progress("evidence_check", ...)
      -> [回调] _run 调用 show_progress("generation", ...)
      -> [回调] _run 调用 show_progress("citation_validation", ...)
      -> [回调] 引用校验失败时调用 "repair"，修复后再调用 "citation_validation"
  -> [回调] run 调用 show_progress("complete", ...)；出现异常时调用 "error"
  -> run 返回 AnswerPipelineResult 给 UI
```

- 每次回调执行时，`run` 都还没有结束；`show_progress` 执行完会回到流水线，流水线再继续往下走；
- 传给检索流水线时，`_run` 又包了一层 `lambda stage, message: self._emit_progress(progress_callback, stage, message)`。检索流水线自己直接调用回调、没有异常保护，包这一层后，检索阶段的通知也能“不传就跳过、出错不中断”，并且会写日志。

#### 回调的“真实逻辑”在哪里

`callback(stage, message)` 这一行本身没有实现，执行哪段代码取决于调用方传入了什么：

| 调用方 | 传入的回调 | 实际效果 |
|---|---|---|
| Streamlit 界面 `ui/app.py` | `show_progress` | 更新页面状态框 |
| CLI `answer` 子命令 `cli.py` | 不传，为 `None` | 不执行回调，只写日志 |
| 测试 `tests/test_answer_pipeline.py` | `lambda stage, message: events.append((stage, message))` | 记录阶段，断言顺序是否正确 |

阅读技巧：遇到“调用一个参数”的代码，跳转到定义只会停在参数声明处。应该反过来找调用方，搜索 `progress_callback=`，看谁传进来了什么函数。

#### 为什么不把 show_progress 写进 answer_pipeline.py

- 拿不到状态框：`progress` 由 UI 在每次提问时用 `st.status(...)` 临时创建，只在 `with` 块内有效；而流水线是 `@st.cache_resource` 缓存的长期实例，不知道当前是哪个状态框；
- 拖累 CLI 和测试：流水线一旦 `import streamlit`，CLI 运行 `answer` 也要依赖 Streamlit，测试也得模拟 Streamlit 组件；
- 难以扩展：以后 `api/main.py` 接入回答流水线，可以自己写一个把进度推给前端（如 SSE / WebSocket）的函数传进来，流水线不用改；
- 保持单向依赖：现在是 `ui/app.py` 依赖 `generation/answer_pipeline.py`，如果流水线反过来依赖 UI，就会形成双向依赖，容易出现循环 import。

分工总结：

| 模块 | 负责什么 | 不关心什么 |
|---|---|---|
| `answer_pipeline.py` | 什么时候通知、通知什么内容（stage + message） | 通知最后显示在哪、长什么样 |
| `app.py` 的 `show_progress` | 怎么展示：状态框的状态、标题、折叠 | 流水线内部有哪些步骤、怎么执行 |

这就是关注点分离：业务逻辑和展示逻辑各管各的，通过 `ProgressCallback` 这个很窄的函数签名连接。
