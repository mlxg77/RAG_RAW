分层架构与核心取舍

代码按“数据准备 → 检索 → 生成 → 接入/保障”形成清晰边界。

数据准备层

ingestion/* · schemas.py
把多格式原文变成可追溯 ArticleChunk。

检索与上下文层

retrieval/*
双路召回、RRF、精排、邻条和预算控制。

可信生成层

generation/*
结构化回答、Evidence ID 校验、修复和日志。

交互与质量层

ui/* · cli.py · evaluation/* · tests/*
入口、展示、离线评测与回归保障。

召回互补BM25 负责关键词确定性，Dense 负责语义泛化；RRF 只融合名次，避免异构分数直接相加。
模型只做选择LLM 返回 Evidence ID；法律名、条号、原文和页码均由程序回填，降低引用幻觉。
失败要可控证据不足不生成；引用失败只修复一次；仍失败则固定安全降级，成本和时延有明确上限。
持久化要一致语料原子写出；Dense 加载检查 ID 集合；上下文和引用再次回查原始 ArticleChunk。
来源可追溯law_id、法律层级、条号、页码、source_file、text_hash 贯穿整条链路。
边界显式项目只覆盖 manifest 中的法律，不把检索不到的问题伪装成确定法律结论。
理解项目时建议按顺序阅读：schemas.py → ingestion/pipeline.py → retrieval/retrieval_context_pipeline.py → generation/answer_pipeline.py → ui/app.py。
